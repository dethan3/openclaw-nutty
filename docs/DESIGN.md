# Nutty 跨平台 AI 记忆插件设计

> 状态：调研稿
>
> 更新日期：2026-08-19
>
> 目标读者：产品设计者、插件开发者、存储适配器开发者

## 1. 摘要

Nutty 将从一个面向 OpenClaw 和飞书多维表格的收藏 Skill，升级为由用户控制的跨平台 AI 长期记忆工具。

它解决的核心问题不是“如何再做一个笔记应用”，而是：用户每天和 AI 一起产生大量判断、方案、解释和偏好，但这些信息通常留在分散的会话里，难以重新找到，也无法稳定参与未来的对话。

Nutty 的目标闭环是：

```text
选择性捕获 -> 保留原文 -> 结构化整理 -> 跨会话检索 -> 注入新对话
```

推荐的产品和技术方向：

1. 建立与平台无关的 Nutty Core，统一记忆格式、分类、去重、脱敏和存储路由。
2. 使用 Skill 描述捕获与检索工作流，使用 MCP Server 承担鉴权、在线写入和搜索。
3. 先发布 ChatGPT/Codex + 飞书多维表格 MVP，验证真实使用频率和召回价值。
4. 随后增加 DeepSeek Harness 原生插件，利用其会话事件能力实现更精确的消息捕获。
5. Notion、Google Workspace 和本地数据库作为后续存储适配器接入，而不是分别实现独立产品。

## 2. 背景

当前 Nutty 的 `SKILL.md` 主要完成以下工作：

- 识别链接、想法、项目、任务和其他输入。
- 提取标签和关联项目。
- 将内容路由到飞书多维表格的不同数据表。
- 保留原始输入，并用简短语气确认保存结果。

这套设计适合收集用户主动发送给 Nutty 的内容，但还没有覆盖 AI 会话中的核心场景：

- 保存上一条 AI 回答。
- 保存当前一轮问题与回答。
- 只保存回答中的一个片段。
- 将某个结论标记为决定、偏好或项目上下文。
- 在新对话里搜索并重新使用过去保存的内容。
- 在多个 AI 客户端之间共享同一份用户记忆。

## 3. 问题定义

AI 会话中的知识沉淀存在四个断点。

### 3.1 捕获断点

有价值的内容产生在对话中，但复制、切换应用、创建页面、填写标题和标签的成本太高。用户通常选择“不记”，然后依赖模糊记忆或重新询问。

### 3.2 所有权断点

平台可能保存聊天记录，但记录由平台组织。用户很难获得一份结构稳定、可以迁移、可以跨模型使用的个人知识资产。

### 3.3 检索断点

保存进笔记工具不等于能够重新利用。没有来源、上下文、项目、类型和全文检索时，收藏内容很容易变成新的信息坟场。

### 3.4 上下文断点

过去的会话通常不会自动进入当前任务。用户知道“以前讨论过”，模型却看不到那段讨论，只能重复推导。

## 4. 产品目标

### 4.1 目标

- 让用户用一句自然语言保存上一条回答、当前问答或选中片段。
- 默认保留原始内容，AI 生成的标题、摘要和标签只能作为派生数据。
- 允许用户明确选择哪些内容进入长期记忆。
- 支持从 ChatGPT、Codex、OpenClaw 和 DeepSeek Harness 访问同一份记忆。
- 支持飞书、Notion、Google Workspace 和本地存储等目标。
- 允许在后续对话中搜索、读取和引用已保存内容。
- 提供清晰的存储位置、权限、导出和删除能力。

### 4.2 非目标

第一阶段不追求：

- 静默保存所有聊天。
- 替代完整的 Notion、飞书或文档编辑器。
- 自动把所有历史会话整理成完美知识库。
- 依赖某一个模型平台的私有会话格式作为唯一数据源。
- 默认保存系统提示词、隐藏推理、内部工具参数或凭据。
- 同时完成所有笔记平台的深度集成。

## 5. 产品原则

### 5.1 用户选择优先

默认使用明确触发。用户说“Nutty，保存上一个回答”后才写入长期存储。

半自动建议和规则自动化必须由用户主动开启，并且可以随时关闭。

### 5.2 原文优先

每条记忆区分两类内容：

- 原始内容：用户问题、AI 回答、选中片段和用户备注。
- 派生内容：标题、摘要、标签、分类和关联项目。

派生内容不能覆盖原文。

### 5.3 跨平台核心，平台薄适配

Nutty Core 不依赖 ChatGPT、Codex、OpenClaw、DeepSeek Harness 或某个笔记服务。平台适配器只负责取得当前上下文并调用统一工具。

### 5.4 保存和召回同等重要

只实现写入会制造新的收藏夹。MVP 必须同时提供搜索和读取，使保存内容可以进入未来对话。

### 5.5 可解释的外部写入

每次写入都应让用户知道：

- 保存了什么。
- 保存到哪里。
- 使用了什么标题或标签。
- 是否发生回退或字段丢失。

### 5.6 隐私最小化

Nutty 只保存完成用户目标所需的内容。系统提示词、隐藏推理、访问令牌、内部配置和不必要的个人信息不得进入长期记忆。

## 6. 核心用户场景

### 6.1 明确捕获

```text
Nutty，保存上一个回答。
Nutty，记下这一轮问答。
Nutty，只保存第二部分。
Nutty，把这条作为 OpenClaw 项目的架构决定。
Nutty，保存到飞书，并加上 #MCP #memory。
```

### 6.2 偏好和长期规则

```text
Nutty，记住我以后写设计文档时优先使用中文。
Nutty，把这个编码约定保存为项目偏好。
```

偏好类记忆比普通笔记风险更高。保存时必须显示它将影响什么范围，例如全局、项目或单次会话。

### 6.3 检索和复用

```text
Nutty，找出我以前关于 MCP 鉴权的讨论。
Nutty，把 OpenClaw 项目的架构决定带入当前对话。
Nutty，列出最近一个月保存的产品想法。
```

### 6.4 半自动建议

当系统识别到明确的决定、长期偏好或重要结论时，可以询问：

```text
这看起来是一个项目决定。要让 Nutty 保存吗？
```

建议模式不应阻断正常对话，也不应在每一轮都出现。

### 6.5 每日回顾

后续版本可以生成当天候选记忆，让用户批量确认，而不是自动写入全部对话。

## 7. 捕获模式

| 模式 | 用户体验 | 精确度 | 默认状态 |
|---|---|---:|---|
| 上一个回答 | 保存最近一条 AI 可见回答 | 中到高，取决于平台 | 开启 |
| 当前问答 | 保存最近一条用户消息和 AI 回答 | 中到高 | 开启 |
| 选中片段 | 保存用户明确选择的文本 | 最高 | 平台支持时开启 |
| 手动内容 | 保存用户直接提供的内容 | 最高 | 开启 |
| 建议保存 | Nutty 发现候选后询问用户 | 中 | 默认关闭 |
| 规则自动保存 | 匹配用户规则后自动写入 | 中 | 默认关闭 |
| 全量记录 | 保存所有可见会话 | 高噪声、高风险 | 不推荐 |

## 8. 总体架构

```text
┌─────────────────────────────────────────────────────────┐
│                    AI 对话平台                           │
│ ChatGPT | Codex | OpenClaw | DeepSeek Harness           │
└──────────────────────────┬──────────────────────────────┘
                           │ 平台上下文
┌──────────────────────────▼──────────────────────────────┐
│                   Nutty 平台适配器                       │
│ Skill | OpenAI Plugin | Harness Plugin | OpenClaw Skill │
└──────────────────────────┬──────────────────────────────┘
                           │ 统一工具调用
┌──────────────────────────▼──────────────────────────────┐
│                    Nutty MCP Server                      │
│ 鉴权 | 输入校验 | 写入控制 | 搜索 | 错误处理 | 可观测性 │
└──────────────────────────┬──────────────────────────────┘
                           │
┌──────────────────────────▼──────────────────────────────┐
│                       Nutty Core                         │
│ 记忆模型 | 分类 | 去重 | 脱敏 | 路由 | 适配器接口       │
└──────────────┬──────────────┬──────────────┬────────────┘
               │              │              │
        ┌──────▼─────┐ ┌──────▼─────┐ ┌──────▼─────────┐
        │ 飞书 Base  │ │   Notion   │ │ Google / Local │
        └────────────┘ └────────────┘ └────────────────┘
```

### 8.1 Nutty Core

负责与平台无关的规则：

- 规范化记忆记录。
- 生成稳定 ID 和内容指纹。
- 检测重复记录。
- 执行脱敏规则。
- 路由到目标存储适配器。
- 统一存储错误和外部记录引用。
- 合并多个存储端的搜索结果。

### 8.2 Skill

Skill 负责告诉模型：

- 什么用户意图应触发 Nutty。
- “上一个回答”和“当前问答”应包含哪些内容。
- 什么时候直接保存，什么时候请求确认。
- 如何调用 MCP 工具。
- 如何向用户报告成功、回退和失败。

Skill 不负责保存凭据、直接拼接第三方 API 请求或维护业务数据库。

### 8.3 MCP Server

MCP Server 负责：

- 暴露清晰、受控的保存和搜索工具。
- 为每个用户执行认证和授权。
- 调用 Nutty Core 和存储适配器。
- 返回结构化结果和稳定记录 ID。
- 记录失败率和延迟，但不记录不必要的私密正文。

### 8.4 存储适配器

每个适配器实现相同能力集合：

- 创建记忆。
- 获取记忆。
- 搜索记忆。
- 更新记忆元数据。
- 删除记忆。
- 检查目标结构和权限。

平台不支持某项能力时，适配器必须明确返回限制，不能假装成功。

## 9. 平台集成设计

### 9.1 ChatGPT 和 Codex

OpenAI 的插件架构允许一个插件组合 Skill 和 MCP Server，并在 ChatGPT 与 Codex 的支持界面中共享。Skill 适合描述重复工作流，MCP Server 适合在线数据、认证和外部写入。

参考：

- [OpenAI Plugin architecture](https://developers.openai.com/plugins/concepts/plugins)
- [Build skills](https://developers.openai.com/plugins/build/skills)
- [Build an MCP server](https://developers.openai.com/plugins/build/mcp-server)
- [Define tools](https://developers.openai.com/plugins/plan/tools)

推荐插件形态：

```text
Nutty OpenAI Plugin
├── skills/
│   └── nutty-memory/SKILL.md
├── MCP dependency
└── optional UI
```

重要限制：MCP Server 本身不应被设计成能够读取完整聊天历史。它接收模型根据工具输入结构传入的内容。因此“保存上一个回答”需要由 Skill 在调用工具前解析上下文，并把要保存的内容作为明确参数提交。

这意味着需要区分：

- 模型传递：实现简单，但可能发生截断、整理或转述。
- 选中内容：平台支持选择上下文时，精确度最高。
- 确认 UI：在写入前显示正文、标题、目标和标签，允许用户修正。

MVP 先采用模型传递，并保留原始字段，不要求自定义 UI。后续只有在预览、编辑或多目标选择明显改善体验时才增加 UI。

### 9.2 DeepSeek Harness

DeepSeek Harness 将模型、工具、Skill、会话、存储、循环和 UI 设计为可组合插件，并使用仅追加的会话事件流记录运行轨迹。

参考：

- [DeepSeek Harness 官方介绍](https://www.deepseek.com/harness/)
- [DeepSeek Harness 源码](https://github.com/deepseek-ai/deepseek-harness)
- [DeepSeek Harness 开发者文档](https://deepseek-harness.github.io/deepseek-harness/guide/quickstart)

Nutty 可以使用原生 Harness 插件读取用户可见的会话事件，因此更适合：

- 精确定位上一条回答。
- 保留消息 ID 和会话 ID。
- 实现可配置的建议保存。
- 在保存后把结果写回当前事件流。

安全边界必须独立于 Harness 的完整轨迹能力。即使运行轨迹包含更多信息，Nutty 也只能捕获用户可见消息，不得保存隐藏推理、系统提示词、内部工具参数、子 Agent 私密上下文或凭据。

Harness 当前仍是开发者预览版。`nutty-dsh-plugin` 应保持为薄适配层，不能把核心数据模型或业务规则绑定到可能变化的 Harness API。

### 9.3 OpenClaw

现有 `SKILL.md` 继续作为兼容入口。短期内可以保留 Links、Ideas、Projects、Tasks 和 Inbox 路由，并逐步改为调用统一 Nutty 工具。

迁移完成后，OpenClaw 不再承担飞书字段映射细节，只负责识别用户意图和传递当前上下文。

## 10. 统一记忆模型

现有的 Links、Ideas、Projects、Tasks 和 Inbox 是存储视图，不应继续作为 Nutty Core 的唯一数据模型。AI 对话需要一个统一的 `Memory` 记录，然后由类型和目标适配器决定如何展示。

### 10.1 Memory

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | string | 是 | Nutty 生成的稳定 ID |
| `title` | string | 是 | 用户提供或 AI 生成的短标题 |
| `content` | string | 是 | 用户明确要保存的原始主体 |
| `user_prompt` | string | 否 | 与内容相关的用户问题原文 |
| `assistant_response` | string | 否 | AI 回答原文 |
| `user_note` | string | 否 | 用户在保存时补充的说明 |
| `summary` | string | 否 | 一句话派生摘要 |
| `type` | enum | 是 | 记忆类型 |
| `tags` | string[] | 否 | 规范化标签，不带 `#` |
| `project` | string | 否 | 关联项目名称或稳定 ID |
| `capture_mode` | enum | 是 | 捕获方式 |
| `source` | object | 是 | 来源平台与会话信息 |
| `sensitivity` | enum | 是 | `normal`、`private` 或 `restricted` |
| `content_hash` | string | 是 | 去重和完整性检查使用 |
| `created_at` | datetime | 是 | 首次捕获时间 |
| `updated_at` | datetime | 是 | 最近更新时间 |
| `external_refs` | object[] | 否 | 各存储平台的记录 ID 和可打开链接 |
| `schema_version` | integer | 是 | 数据迁移版本 |

### 10.2 记忆类型

第一版建议支持：

- `conversation`：普通问答或回答片段。
- `decision`：已经做出的项目或个人决定。
- `insight`：值得保留的解释、推论或灵感。
- `reference`：链接、论文、工具或资料。
- `task`：需要执行的行动。
- `project`：项目目标、状态或下一步。
- `preference`：用户长期或项目级偏好。
- `inbox`：类型暂时无法确定的内容。

### 10.3 来源对象

```json
{
  "surface": "chatgpt",
  "conversation_id": "optional-platform-id",
  "user_message_id": "optional-platform-id",
  "assistant_message_id": "optional-platform-id",
  "conversation_url": "optional-user-openable-url",
  "model": "optional-model-name"
}
```

平台没有提供的字段保持为空，不能由模型编造。

## 11. MCP 工具设计

### 11.1 `save_memory`

保存一条明确的记忆。

核心输入：

- `content`
- `capture_mode`
- `source_surface`
- 可选的 `user_prompt`、`assistant_response`、`title`、`type`、`tags`、`project`、`destination` 和 `user_note`

核心输出：

- Nutty 记录 ID。
- 最终标题、类型和标签。
- 实际写入目标。
- 外部记录 ID 或链接。
- 被跳过的字段和原因。
- 是否命中重复记录。

`save_memory` 是外部写入操作。服务端必须执行授权、长度限制、字段校验、脱敏和幂等处理。

### 11.2 `search_memories`

按查询、类型、标签、项目、来源、目标和时间范围搜索。

结果默认只返回标题、摘要、来源、时间和稳定 ID。完整正文通过 `get_memory` 获取，减少不必要的上下文和隐私暴露。

### 11.3 `get_memory`

根据稳定 ID 读取完整记忆。返回原文与派生内容，并明确它来自哪个存储目标。

### 11.4 `update_memory`

修改标题、摘要、标签、项目或类型。更新原始正文需要用户明确说明，不能由自动整理流程静默覆盖。

### 11.5 `list_destinations`

列出已连接存储端、默认目标、可用能力和当前权限状态。

### 11.6 后续工具

- `delete_memory`：明确确认后删除 Nutty 记录及指定外部副本。
- `export_memories`：导出用户拥有的数据。
- `suggest_memories`：从用户可见会话中返回候选项，不直接写入。

读取和写入工具必须分离，避免权限和选择逻辑混淆。

## 12. 存储设计

### 12.1 MVP：飞书多维表格

推荐新建单一 `Memories` 表，并通过视图展示不同类型，而不是要求每种记忆都进入独立数据表。

理由：

- 一轮对话可能同时包含决定、参考资料和任务。
- 单表更容易实现统一搜索、去重和迁移。
- 视图仍然可以提供 Links、Ideas、Projects 和 Tasks 的使用体验。

为了兼容现有 Collector_Base，飞书适配器提供两种配置：

- `unified`：推荐模式，写入 `Memories`。
- `legacy`：继续映射到 Links、Ideas、Projects、Tasks 和 Inbox。

### 12.2 Notion

建议映射到单一数据库，正文较长时可以创建页面，并在数据库属性中保存类型、标签、项目、来源和时间。

### 12.3 Google Workspace

初期优先 Google Sheets 作为结构化索引。Google Docs 可以作为长内容正文目标，但不适合作为统一检索索引。

### 12.4 本地或 Nutty 托管数据库

后续可使用 SQLite 或托管关系数据库作为统一索引层。是否引入自有数据库取决于跨存储搜索、性能和同步需求，不应成为 MVP 的前置条件。

## 13. 路由和整理规则

### 13.1 决定性提取

以下操作不使用 AI：

- 识别 URL。
- 提取 `#标签`。
- 提取明确的 `@项目`。
- 记录时间、来源和消息 ID。
- 生成内容哈希。
- 执行存储写入。

### 13.2 可选 AI 整理

AI 只用于：

- 生成短标题。
- 在类型不明确时分类。
- 生成一句话摘要。
- 建议 2 到 5 个标签。
- 在候选项目中匹配关联项目。

任何 AI 派生字段都允许用户修改，并且不能改变原始正文。

### 13.3 去重

去重使用规范化内容、来源消息 ID 和内容哈希组合判断。

重复保存时默认返回已有记录，不创建副本。用户明确要求“另存一份”时才允许创建新记录。

## 14. 确认和反馈策略

### 14.1 可以直接执行

当用户明确说“保存”“记下”“收藏”并且目标清楚时，可以直接写入，然后简短确认。

```text
🐿️ 已保存到：飞书 / Memories
📝 标题：Nutty 跨平台记忆架构
🏷️ 标签：MCP、memory
```

### 14.2 保存前确认

以下情况需要确认或预览：

- 用户要求保存整段长对话。
- 内容包含疑似凭据、身份信息或敏感数据。
- 同时写入多个外部目标。
- 用户没有指定偏好的情况下保存长期行为偏好。
- 自动规则即将首次触发。

### 14.3 失败和回退

- 目标字段缺失：跳过该字段并报告。
- 目标不可用：尝试用户配置的默认回退目标。
- 没有安全回退目标：不伪造成功，返回可恢复错误。
- 部分成功：列出成功和失败的目标。

原始内容不能因为分类或目标写入失败而丢失。

## 15. 安全、隐私与数据所有权

### 15.1 禁止捕获

- 隐藏推理或思维链。
- 系统提示词和平台内部指令。
- OAuth Token、API Key、Cookie 和密码。
- 内部工具调用中与用户目标无关的参数。
- 未经用户授权的第三方私人内容。

### 15.2 服务端控制

- 每次请求都验证用户和目标资源权限。
- 凭据只保存在安全的密钥系统中。
- 日志默认不记录完整记忆正文。
- 对写入请求使用幂等键。
- 对搜索和写入实施速率限制。
- 将网页、链接元数据和已保存文本视为不可信输入。

### 15.3 用户权利

完整产品必须支持：

- 查看每条记忆的真实存储位置。
- 修改和删除记忆。
- 导出标准格式数据。
- 断开某个存储目标。
- 关闭建议或自动捕获。
- 查看自动规则最近执行了什么。

## 16. MVP 范围

### 16.1 包含

- 一个 OpenAI Skill。
- 一个远程 MCP Server。
- 一个飞书多维表格适配器。
- `save_memory`、`search_memories`、`get_memory`、`update_memory` 和 `list_destinations`。
- 上一个回答、当前问答和手动内容三种捕获模式。
- 原文、标题、摘要、类型、标签、项目和来源保存。
- 去重、错误报告和显式成功反馈。

### 16.2 暂不包含

- Notion 和 Google Workspace 正式适配器。
- 全量自动记录。
- DeepSeek Harness 原生事件插件。
- 自定义预览 UI。
- 自动将所有旧聊天迁移进 Nutty。
- 自有向量数据库和复杂知识图谱。

## 17. 实施顺序

### 阶段 0：调研与规格

- 确认 ChatGPT/Codex 对前一条消息、选中文本和插件 UI 的实际上下文能力。
- 确认 DeepSeek Harness 会话事件、插件生命周期和权限接口。
- 定义统一 Memory Schema 和存储适配器契约。
- 决定飞书使用 unified 还是 legacy 模式。

### 阶段 1：GPT/Codex + 飞书 MVP

- 实现 Nutty Core。
- 实现 MCP 工具和飞书适配器。
- 重写 Skill，使其处理对话捕获和检索。
- 完成明确触发、保存反馈和失败回退。
- 使用真实日常对话连续验证两周。

### 阶段 2：DeepSeek Harness 适配

- 实现薄原生插件。
- 使用用户可见会话事件精确捕获消息。
- 验证建议保存和每日候选记忆。
- 比较模型传递与原生事件捕获的准确率。

### 阶段 3：多存储与交互

- 增加 Notion 和 Google Workspace 适配器。
- 增加预览、编辑和目标选择 UI。
- 增加导出、删除和同步状态管理。

### 阶段 4：长期记忆闭环

- 改善跨目标搜索和排序。
- 支持按项目生成上下文包。
- 在用户确认后把相关记忆注入新对话。
- 建立记忆过期、合并和冲突处理机制。

## 18. 成功指标

第一阶段不以保存总量为主要指标。核心指标应反映记忆是否真的有用：

- 每周主动捕获次数。
- 捕获后 30 天内被搜索或读取的比例。
- 搜索后被带入当前任务的比例。
- 用户修改 AI 标题、分类或标签的比例。
- 重复保存拦截率。
- 保存成功率和 P95 延迟。
- 因隐私检测而请求确认的次数与用户决定。
- 连续两周仍主动使用 Nutty 的测试用户比例。

需要特别观察三类失败：

- 用户想保存，但 Skill 没有触发。
- Nutty 保存了错误范围或非原文内容。
- 内容已经保存，但用户之后找不到或没有想到去找。

## 19. 已做出的设计决定

| 决定 | 理由 |
|---|---|
| 核心跨平台，入口薄适配 | 避免为每个 AI 客户端重复实现业务规则 |
| GPT/Codex 先发布 | 优先在用户高频对话环境验证需求 |
| DeepSeek Harness 第二阶段 | 原生事件捕获价值高，但平台仍处于开发者预览期 |
| 飞书作为第一个存储端 | 复用现有项目基础和用户配置 |
| 默认明确触发 | 控制噪声、隐私和误保存 |
| 保存与搜索同时进入 MVP | 没有召回能力的收藏不会形成记忆闭环 |
| 原文与 AI 派生字段分离 | 防止摘要或分类破坏信息真实性 |
| Skill + MCP Server | Skill 处理工作流，服务端处理认证和外部状态 |

## 20. 待调研问题

### OpenAI

- ChatGPT 和 Codex 在工具调用时能否稳定传递上一条完整回答？
- 不同界面对选中文本和消息引用提供什么上下文？
- 哪些外部写入需要平台级确认或特殊安全标注？
- 公共插件、私有插件和开发者模式的发布与认证要求有什么差异？

### DeepSeek Harness

- 插件读取用户可见消息事件的稳定接口是什么？
- 如何区分可见回答与隐藏运行轨迹？
- 插件能否附加自定义记忆元数据而不修改原始事件？
- 插件 API 在开发者预览阶段的兼容策略是什么？

### 存储

- 飞书单表 unified 模式是否满足日常检索和视图需求？
- 多个存储端同时启用时，哪个系统作为事实来源？
- 外部记录被用户直接修改或删除后如何同步？
- 是否需要 Nutty 自有索引来支持跨平台搜索？

### 产品

- 用户最常保存回答、完整问答，还是选中片段？
- 用户更需要原文检索，还是项目上下文包？
- 什么情况下建议保存有帮助，什么情况下会打扰用户？
- 哪些记忆应该过期、合并或升级为长期偏好？

## 21. 结论

Nutty 不应被定义为“把 ChatGPT 回答写入飞书的插件”。更持久的定位是：

> Nutty 是由用户控制、跨 AI Harness 工作的个人长期记忆层。

产品架构从第一天支持多个平台，但实现顺序保持克制：先完成 GPT/Codex + 飞书的保存和召回闭环，再接入 DeepSeek Harness 的精确事件捕获，最后扩展多存储、自动建议和上下文注入。

这个顺序优先验证真正的用户价值：人们是否愿意选择性保存，以及保存的内容是否会在未来再次帮助他们。
